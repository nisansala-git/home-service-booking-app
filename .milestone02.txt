c. Wireframes derived from selected sketches (You can see all the
Wireframes done by members separately in this link -
https://www.figma.com/design/R5hLGZoQA17qz99JdphyHa/IT3060-
Milestone-02---Home-Service-Booking---KND_HCI_G05?node-id=1-2)

1. Home / Service Discovery — Selected: Variant A

Justification: We went with the category-grid version because our own homeowner
interviewee found her plumbing category "without much difficulty" using this exact
layout style on Profit.lk — it's a proven pattern for first-time discovery, and most
homeowners in our survey said they book only 1–2 times a year, so personalization
for a "returning user" mattered less than we first thought.

Structure (top to bottom): App header + registration CTA → search bar → quick
filter chips (Top rated / Nearby / Available today) → "Browse by category" grid →
promo banner → "Providers near you" list → bottom nav.




2. Search Results + Filters — Selected: Variant A

Justification: The flat list with individual filter buttons (Price, Rating, Availability,
Distance) won out because it keeps every relevant detail — rating, distance, price,
verified badge — visible in a single row, which matters directly for Theme 4 from
our research (everyone wants visible trust signals without extra taps).

Structure: Back + search bar → filter button row → result count + sort → provider
cards (name, category, rating, distance, badges, price, View button) → bottom
nav.




3. Provider Registration Form — Selected: Variant A

Justification: We kept the single continuous form rather than the multi-step
wizard because our carpenter interviewee already struggled at just the verification
step; adding more discrete steps before he even reaches verification risked more
places for him to abandon the flow.

Structure: Back + title → Full name, Phone, Email, Password, Confirm password
fields → Service category dropdown → Service area field → Upload
ID/certification → terms checkbox → Create account button.




4. Provider Registration & Verification — Selected: Variant B

Justification: This is the direct fix for Theme 3 in our findings — the carpenter's
OTP never arrived and he had no idea what to do next. Giving verification its own
screen with a step indicator and a visible "Trouble verifying by SMS? Continue
verification on website" link is our answer to that exact failure (FR002, NFR001,
NFR003).

Structure: Back + step indicator (Info → Verify → Details) → "Verify your number"
heading → 6-digit code input → delivery-monitoring note → error state ("Incorrect
code, 2 attempts left") → resend timer → website fallback link → Continue
button.
5. Provider Profile — Selected: Variant A

Justification: Putting the upfront pricing table as the very first content block
responds directly to our homeowner's complaint about unclear pricing (Theme 1) —
she shouldn't have to tap into a separate tab to see what something costs.

Structure: Cover photo + provider name/rating/verified badge → Upfront pricing
table → About → Past work gallery → Booking history stats (jobs completed / on-
time % / years) → Verified reviews → sticky "From Rs X / Check availability"
footer.




6. Availability & Booking — Selected: Variant B

Justification: The Morning/Afternoon grouping is simply easier to scan once the
slot list grows, and the explicit note about what happens if two people tap the
same slot ties straight back to NFR007 — our developer's concern about handling
booking conflicts at scale.

Structure: Back + date strip (Mon–Sun) → Morning slots → Afternoon slots →
conflict-handling note → sticky footer with service summary, price, and Book Now
button.




7. Booking Confirmation — Selected: Variant B

Justification: A checkmark alone doesn't fix Theme 2 — our homeowner expected
confirmation but felt the process still ended on uncertainty. The "What happens
next" stepper (Confirmed → Sign contract & pay deposit → Provider arrives) turns
confirmation into the start of a visible process rather than a dead end.

Structure: Confirmed badge + heading → ticket-style summary card (provider,
service, price, date/time, location, booking ID + barcode) → "What happens next"
progress stepper → Done button.
8. Digital Contract & Deposit — Selected: Variant B

Justification: Condensing the agreement into scannable Key terms bullets, with a
clear Deposit-due-now vs. Remaining-after-job split, is what actually
communicates the numbers our carpenter asked for — a full legal wall of text
(Variant A) doesn't get read.

Structure: Back + "Confirm & agree" heading → Key terms bullet list → "Read full
agreement" link → deposit/remaining split bar → signature pad → agreement
checkbox → "Accept & pay [amount] deposit" button.




9. Secure Payment & Receipt — Selected: Variant B

Justification: The icon-based method picker plus a saved card speeds up a return
payment, and the share-receipt icons (email/download/print) reflect a real,
practical need — keeping proof of payment for later — that a plain download link
doesn't fully cover.

Structure: Back + "Payment" heading + encryption note → payment method icons
(Card/Wallet/Bank) → saved card row → amount due + "Pay securely" button →
Digital receipt card (service, payment method, deposit paid, share icons) → Done
button.




10. Completed Job & Review — Selected: Variant A

Justification: We chose the single overall star rating with an optional text box over
the more granular Quality/Punctuality/Professionalism split, since keeping this
step low-effort matters more than the extra data — a review a homeowner actually
finishes is more useful than a detailed one they abandon halfway.

Structure: Back + "Job completed" checkmark → job summary → 5-star rating →
optional review text box → Submit review button → "Skip for now" link → trust
note about reviews being public/verified.
11. Provider Dashboard / Job Requests — Selected: Variant A

Justification: Showing all new requests plus today's confirmed schedule on one
screen means Kamal doesn't lose visibility of jobs he's already committed to while
deciding on new ones — the swipe-one-at-a-time alternative hid that schedule
entirely.

Structure: Greeting + Online toggle → "New requests" list with Accept/Decline per
card → "Today's schedule" list → bottom nav (Requests/Bookings/Profile).




12. Provider Notifications & Job Details — Selected: Variant B
Justification: A running notification list (new request, contract signed, deposit
received) gives the provider a record of everything that's happened on a job — this
maps directly to our Theme 5 finding that providers specifically wanted
notifications for job-related updates, not just the newest one.

Structure: "Notifications" heading → chronological notification list (newest
highlighted) → "Job details" card → job status progress list (Request accepted →
Contract signed → Deposit received → Job in progress) → Get directions / Message
customer buttons.




13. My Bookings / Job History — Selected: Variant A

Justification: We kept this to a plain tabbed list rather than adding the
earnings/stats header — for a homeowner-facing bookings screen specifically,
seeing your own bookings clearly mattered more than monthly stats, which is
really a provider-side need.

Structure: Heading + My Bookings/Job History tabs → booking cards with status
badge (Confirmed/Completed/Awaiting deposit), provider, date, price → bottom
nav.

14. Job History — Selected: Variant B

Justification: We dropped the four-field search form (date range, status, service
type, customer name) since a small job history doesn't need it yet — going straight
from tab to completed-jobs list matches how a provider would actually expect to
check recent work, without extra setup first.
Structure: Heading → My Bookings/Job History tabs → completed job cards
(customer, date, rating given, price, status) → bottom nav.




d. Low-Fidelity Prototype and How It Was Validated/Refined

We linked our selected wireframes into two clickable Figma prototypes covering
the full homeowner and provider flows, using native frame-to-frame connections.
Validation was done by checking each screen against the FR/NFR list from
Milestone 01 as we built it, rather than after the fact — confirming every
requirement had a dedicated interface. This is why screens like Provider
Registration & Verification (FR002/NFR001/NFR003) and Digital Contract & Deposit
(FR006) exist separately rather than being merged into other screens, since each
addresses a specific pain point from our interviews. Coverage was complete by the
end of this stage, so the flow needed no major restructuring — all 14 interfaces
map cleanly to the requirements (see traceability table, Section a). Formal
usability validation with real users was carried out later, after the high-fidelity
prototype was built (Section f/g).




e. High-fidelity prototype screenshots and interaction flow

Tool used: Figma, chosen for its native prototyping (frame-to-frame click connections,
overlays, and component variants), which let us build both the homeowner and
provider flows as fully interactive, shareable prototypes without exporting to a separate

f. User testing plan (tasks, success criteria, metrics)

Method: Moderated remote testing conducted individually with each participant. Every
participant shared their screen while completing a task on the Figma high-fidelity
prototype, thinking aloud as they navigated. Sessions were observed live and recorded
(See here)

Participants: 4 real users tested to date — 2 completed the homeowner booking flow, 1
(Sulani) completed a plumbing-specific search-and-book flow, and 1 completed the
service provider registration and job history flow, together covering both stakeholder
tiers identified in Milestone 01.

What worked well: All four participants found core discovery and browsing easy —
User 01/02 called finding a provider straightforward, User 03 said the app "felt like
a normal app I would actually use," and User 04 found reviewing past bookings in
one place easy once located. Visible upfront pricing paired with reviews on the
Provider Profile screen was specifically called out as building trust, and the visual
design (color palette, text size, promotional banner) was well received by User 03
— supporting the design decisions made in Sections (b)–(c) and (e).

Limitation: Testing was completed with 4 of the 5 participants required by the
assignment. Findings above reflect real, consistent feedback across both
stakeholder tiers, but a fifth session is recommended to fully satisfy the
assignment's testing requirement.
